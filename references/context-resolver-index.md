# Context Resolver Index

Status: initial annotated routing artifact

Source: `ARCHITECTURE.md` Context Resolver Principle.

## Purpose

This index tells Samantha what to read first when a task signal appears. It is a
manual routing aid, not resolver code, automatic context loading, hidden memory,
or a broad repository index.

Use the smallest matching route. Top-level documents should stay pointers to
authority and product boundaries; narrower playbooks, templates, run evidence,
or candidate artifacts should carry the task-specific detail. If the route does
not match the current task, do not preload it.

## Initial Routes

| Route | Task signal | Read-first artifacts | Why those artifacts matter | When not to read them | Authority limits |
| --- | --- | --- | --- | --- | --- |
| Brainstorm / plan | `Samantha brainstorm:` or `Samantha plan:`; open product, architecture, sequencing, or MVP-scope decisions; accepted direction may need a later executable slice. | `OPERATING_GUIDE_KR.md`; `references/playbooks/samantha-brainstorming.md`; `references/playbooks/initiative-continuity-brief.md` when the result spans multiple slices; `NORTH_STAR.md` or `ARCHITECTURE.md` only when the decision touches product or authority boundaries. | Keeps exploratory work at the right intent level, forces explicit decisions and rejected alternatives, and preserves multi-slice direction only when BK accepts that artifact. | Do not read the brainstorm stack for a decision-complete command with target files and verify commands, or for a local report-only question that does not need product direction. | Brainstorming and planning may inspect, clarify, and draft direction. They do not authorize code edits, task dispatch, worktree creation, commits, lifecycle mutation, or treating temporary visuals as accepted requirements. |
| Doctrine update | Proposed changes to `AGENTS.md`, `NORTH_STAR.md`, `ARCHITECTURE.md`, `ROADMAP.md`, or any rule that changes Samantha's product boundary, authority model, or MVP scope. | `AGENTS.md`; `NORTH_STAR.md`; `ARCHITECTURE.md`; `ROADMAP.md`; `WORK-RULES.md`; the narrower artifact whose boundary would change. | These files define product boundary, architecture, roadmap, and work discipline. Reading them first prevents contradictory doctrine and keeps top-level docs as boundary pointers instead of dumping every lesson into them. | Do not read the full doctrine set for a narrow playbook copy edit, lesson candidate, or docs-only reference change that does not move authority or product direction. | Doctrine updates are documentation-only unless enforcement is explicitly requested. Authority-moving changes should get report-only review before becoming routine and must not silently create policy code, task templates, runtime behavior, or hidden memory. |
| Policy change | Dispatch, scope, verification, merge, lifecycle, cleanup, template/profile, or contract behavior would accept, reject, or grant authority differently. | `ARCHITECTURE.md` policy and meta-task sections; `src/core/policy.ts`; `tests/policy.test.ts`; affected task templates, agent profiles, or contract types; `WORK-RULES.md` for implementation discipline. | Policy is the deterministic trust gate. The tests must prove both the intended accept path and reject path, and affected templates or profiles show where authority is surfaced to workers. | Do not use the policy route for advisory playbook wording, doctrine-only explanation, or a docs-only task that does not change dispatch or trust decisions. | Policy changes require focused tests. They do not grant workers merge, push, cleanup, dispatch, lifecycle, doctrine, or promotion authority, and they should not rewrite doctrine unless a separate doctrine task authorizes it. |
| Self-build task spec lifecycle | Samantha self-build work asks whether a task spec should live in `references/tasks/<id>.json` or outside the repo; questions about committing a planning task spec before dispatch; questions about clean worker bases that include task specs; questions about post-run backfill of `references/tasks/**`. | `references/playbooks/self-build-task-spec-lifecycle.md`; `WORK-RULES.md` Self-Build Task Spec Lifecycle section; `OPERATING_GUIDE_KR.md` authority boundary section. | The playbook defines the persistent vs ephemeral spec choice, exact pre-dispatch gates, post-run restrictions, authority limits, verification expectations, and stop conditions before lifecycle mistakes turn into trusted run evidence. | Do not use this route for ordinary docs-only edits, task template changes, policy implementation, failed-run diagnosis, or broad doctrine work unless the task spec lifecycle question is the actual issue. | This route is advisory lifecycle guidance. It does not authorize workers to create task specs, dispatch, commit, push, mutate lifecycle state, clean worktrees, promote temporary specs, or add CLI/runtime/policy automation. |
| Failed-run recovery | A run ended `blocked`, `rework`, malformed, scope-failed, verify-failed, stale, or otherwise untrusted, and Samantha needs the next explicit task or lifecycle action. | Source run log under `runs/`; the original task spec when available; `ARCHITECTURE.md` Failure Recovery Model; relevant `ROADMAP.md` recovery slice; generator code and tests only when the recovery mechanism itself is changing. | Failed worker output is evidence, not trusted state. These artifacts preserve the failure class, failed command, target scope, and allowed recovery action before creating a narrower follow-up. | Do not read recovery artifacts for a fresh feature request, a report-only review without run evidence, or a clearly transient environment failure that only needs a visible rerun decision. | Recovery may classify evidence and propose a narrower task or lifecycle action. It must not trust failed output, retry invisibly, accept unverified changes, mutate lifecycle as a worker, or skip the failed verification in the follow-up. |
| Learning / lesson promotion | Repeated run evidence, `lessons:draft`, `lessons:review`, `lessons:review-inbox`, `lessons:promote`, or a candidate that may become durable guidance. | `ARCHITECTURE.md` Learning Artifact Layer; `references/playbooks/learning-trigger-policy.md`; the specific candidate under `references/lessons/inbox/`; matching review records under `references/lessons/reviews/`; the proposed promoted artifact only after the review path points to it. | The learning loop separates evidence, candidate, review, promotion, and later evidence. It keeps durable guidance reviewable and prevents one-off failures from becoming doctrine or policy. | Do not use this route for a one-off preference, an uncited hunch, a direct bug fix, or correction evidence that first belongs in correction transcript mining. | Drafting does not promote. Promotion requires explicit review, no hidden memory, and the smallest fitting artifact layer. Trust gates belong in policy code with focused tests, not in advisory lesson text. |
| Correction transcript mining | BK supplies or points to a correction excerpt, review comment, or run evidence showing Samantha/Codex missed, overreached, or should learn a routing or behavior lesson. | `references/playbooks/correction-transcript-mining.md`; the explicit session excerpt, review comment, or named run evidence; affected-layer artifacts only as context for the candidate. | The playbook defines allowed evidence, candidate fields, classifications, review flow, stop conditions, and the boundary between mining and promotion. | Do not use this route to hunt through private transcripts, infer unstated preferences, scan automatically, or implement the proposed fix directly. | Mining creates candidates only. It must not promote, edit durable artifacts, create automation, add resolver code, change policy, dispatch workers, write hidden memory, or mutate lifecycle state. |
| Batch planning | Multiple writer tasks, dependencies, write-set separation, serial-only files, integration order, stale-base behavior, or BatchSpec lifecycle is in scope. | `ARCHITECTURE.md` Parallelism Boundary; `ROADMAP.md` Phase 5; `references/batch-specs/phase-5-minimal-batch-spec.md`; `references/batch-specs/phase-5-writer-batch-execution-design.md`; the source BatchSpec when one already exists. | Batch artifacts prove dependency, write-set, integration, stale-base, partial-failure, and cleanup decisions before dispatch. They also keep parallel execution separate from parallel trust. | Do not read batch planning docs for a single writer task, docs-only task, or report-only parallel review that does not create or mutate a BatchSpec. Use doctrine or policy routes instead when a serial-only authority boundary is the real subject. | Samantha owns batch orchestration, preflight, dispatch order, integration, verification, lifecycle records, and cleanup. Workers must not spawn agents, mutate BatchSpecs, raise writer concurrency, merge, rebase, or decide cleanup. |
| Docs-only writer task | Target files are markdown only; executable code, tests, task specs, templates, profiles, run logs, worktrees, and package metadata are out of scope; cheap markdown verification is enough. | The exact target markdown files; `references/task-templates/docs-only.json`; the source principle, playbook, or direction document the edit extends. | Keeps documentation work surgical, tied to declared target files, and verified with a markdown-surface check instead of broad unrelated test runs. | Do not use this route when executable behavior, policy, contracts, templates, profiles, run evidence, package metadata, or generated artifacts must change. | Docs-only writers may edit only authorized markdown. They must not touch source, tests, templates, profiles, run logs, worktrees, package files, runtime adapters, daemon behavior, dashboards, routine triggers, or hidden memory. |
